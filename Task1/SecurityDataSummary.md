# Сводка по конфиденциальным данным и безопасности

## 1. Аудит As-Is
- Доступ: AD без MFA; нет RBAC/ABAC по доменам и атрибутам.
- Хранение: файлы (Excel/JPG/PDF) без шифрования на покое; e-mail без сквозного шифрования.
- Логирование: отсутствует аудит чтения/изменений медданных и PII.
- Минимизация: собираются лишние поля, нет сроков хранения и процедур удаления.
- Целостность/Lineage: дубли, рассинхрон; нет Data Lineage.
- Резервирование/ДРС: не описано для критичных данных.
- Интеграции: обмен с лабораторией через Excel-реестры без защищённых API/контрактов.

## 2. Неучтённые конфиденциальные данные (категории)
- HEALTH: результаты анализов/заключения в JPG/PDF вне учёта.
- PII: ФИО/ДР/контакты/адрес в Excel и сканах без реестра атрибутов.
- Финансы: договоры/квитанции/экспорт ККМ, дубли в Excel.
- Операционные журналы: списки ресепшена/кассы/склада с PII.
- E-mail вложения: пересылка HEALTH/PII без DLP и классификации.
- Реестры лаборатории: Excel с PII/HEALTH вне контролируемого API.
- Метаданные/бэкапы: EXIF/Office свойства/теневые копии — риск утечки.
- ТМЦ: накладные/серийники, позволяющие деанонимизацию пациента.

## 3. Проблемные зоны
- Ручные процессы и неструктурированное хранение → ошибки/утечки.
- Нет тонкого разграничения доступа и принципа «need-to-know».
- Нет аудита/трассируемости действий с данными.
- Неконтролируемые потоки между системами и через почту.
- Несоответствие требованиям к ПДн и медданным (HEALTH).
- Риски масштабирования: рост объёма данных усугубит проблемы.
- Интеграция с лабораторией без безопасных контрактов.

## 4. Процессы → практики (PbD/DM/DL) и акценты
- 1. Запись: минимизировать PII; RBAC к журналу; фиксировать изменения.
- 2. Регистрация: согласия и прозрачность; только нужные атрибуты; lineage до карточки/папки.
- 3–4. Платежи: разделение ролей касса/бух; маскирование реквизитов; трассировка от ККМ/Excel до 1С и отчётности.
- 5. ТМЦ: исключить связь с пациентами; хранить только движение; lineage накладных/проводок.
- 6. Медкарта: изоляция кабинетов; роль/атрибут-доступ; версии и аудит документов.
- 7. Лаборатория: защищённые API, минимальный состав; журнал обмена/использования.
- 8. Почта: DLP/запрет внешних рассылок HEALTH/PII; журнал отправок/скачиваний.

## 5. Данные → способы защиты
- PII: Encrypt-at-Rest, TLS, маскирование UI, RBAC/ABAC, контроль экспорта.
- HEALTH: шифрование (KMS), аудит доступа/версий, псевдонимизация/обезличивание для аналитики.
- Финансы/договоры: роли касса/бух, маскирование реквизитов, ЭЦП/хэш целостности.
- Журналы/операционные списки: классификация, запрет внешней передачи, DLP/watermark.
- Реестры интеграций: API-контракты, минимизация полей, токены с ограничениями, шифрование канала/файлов, журнал выдачи/получения.

## 6. Тегирование
- Категории: PII, HEALTH, FINANCE, CONTRACT, INTEGRATION, INTERNAL, EMAIL; уровни чувствительности S1–S3.
- Обязательные атрибуты: владелец домена, срок хранения, правовое основание.
- Присвоение: автоклассификация на входе (формы/API), сканирование файлов + ручное подтверждение.
- Применение: RBAC/ABAC по тегам, маскирование/псевдонимизация (HEALTH/PII), DLP-правила (EMAIL/INTEGRATION).
- Хранение: Data Catalog (OpenMetadata/Amundsen/DataHub), версии и аудит тегов.

## 7. Инструменты и меры по потокам
- Базовые: TLS/mTLS, Encrypt-at-Rest (KMS), RBAC/ABAC, DLP, Audit/Lineage, Masking, Integrity/Signed, Secure Channel.
- Конкретика: AD+MFA, Vault/KMS, роли 1С (Бух/ТиС), API Gateway, Exchange Transport Rules/O365 DLP, SIEM.
- На DFD (Level 1) пометки добавлены на потоках/операциях: TLS/mTLS, Encrypt-at-Rest, RBAC/ABAC, DLP, Audit, Masking, Integrity.

## 8. Приоритеты улучшений
1. Внедрить RBAC/ABAC и MFA.
2. Включить шифрование данных на покое и в каналах.
3. Ввести централизованный аудит и Data Lineage.
4. Настроить DLP для почты и файлов.
5. Реализовать защищённый API с лабораторией.
6. Внедрить каталог данных и тегирование.
7. Утвердить политики минимизации и удаления данных.
