# Стратегия миграции

## Рассмотренные подходы

### Вариант 1. Greenfield (High‑level design c нуля)
Полный запуск новой системы «с чистого листа» позволяет переосмыслить процессы и архитектуру. Однако это:
- требует длительного времени на проектирование, разработку и обучение;
- повышает риски ошибок на старте;
- усложняет откат — несовместимость со старой моделью.

Итог: для текущего контекста — не рекомендуем.

### Вариант 2. Parallel Run (параллельная работа)
Запуск новой системы одновременно со старой. Проблемы:
- сложная и затратная синхронизация (ручные Excel/файлы ↔ новая платформа);
- формирование двух нестабильных контуров (старые риски + новые баги);
- сложность классификации/триажа инцидентов.

Итог: нецелесообразно.

### Вариант 3. Branch by Abstraction (выбранная стратегия)
Постепенная замена функциональности через слой абстракций:
- минимальные простои, возможность безопасного отката по feature‑toggle;
- плавные изменения для пользователей (минимум сопротивления);
- управляемая миграция данных и интерфейсов.

Итог: рекомендуемая стратегия.

## Риски Branch by Abstraction и меры
- Неверные границы абстракций → детальная декомпозиция, ревью дизайна, DDD.
- Расхождения данных при параллельных реализациях → контрольные точки, верификация и reconcile‑скрипты.
- Поддержка двух реализаций в переходный период → четкий регламент включения/отключения, автоматизированные тесты.

## Принцип перехода интерфейсов
Сначала вводим единый web‑интерфейс поверх текущего источника (файловая модель), затем переключаем абстракцию на целевые сервисы (CRM/EHR и т. п.). Для пользователей изменения происходят итеративно, без резких разрывов.

## Роли и зоны ответственности
- Технический директор: архитектура, безопасность, технологические решения, сроки.
- Администратор сети: инфраструктура, деплой, интеграции, бэкапы, мониторинг.
- Бизнес‑аналитик: требования, тест‑сценарии, сверка данных, отчеты.
- Ресепшен / Касса / Склад / Бухгалтерия: обратная связь, приемочные испытания.
- Медицинские специалисты: тестирование пользовательских сценариев, обратная связь.
- Фронтенд‑разработчик (найм): разработка web‑порталов.

Этот план позволяет поэтапно перенести критические операции на новые сервисы, сохранить управляемость рисков и обеспечить прозрачность для пользователей за счет абстракций и feature‑toggle.
